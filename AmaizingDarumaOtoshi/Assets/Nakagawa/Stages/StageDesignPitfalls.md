# ステージ設計の注意点（モデル向け）

AI がステージを設計・実装するときに起こりがちな失敗と、その避け方。
世界観と仕様は同じフォルダの `WorldSetting.md` を先に読むこと。設計案を出す前と、実装を終えたあとに、このチェックリストを見直す。

---

## 1. 色と見やすさ（特に多い）

一画面に、4人のプレイヤー・たくさんの積み木・ギミック・エフェクト・HUD が同時に映る。
見づらくなる原因は色の数そのものではなく、**同じ色が複数の意味で使われること**。
ステージやギミックを足すたびに色を足すと、色を見ても「それが何か」が分からなくなる。

### 1-1. すでに意味が決まっている色を、別の意味で使ってしまう
次の色は役割が決まっている。ステージの床・壁・飾り・新しいギミックに、同じ色を鮮やかなまま使わない。

| 色 | 意味 | 決めている場所 |
|---|---|---|
| 鮮やかな赤・青・黄・緑 | 積み木の色。プレイヤー番号の色（1P 赤・2P 青・3P 黄・4P 緑。輪郭と出現位置の印） | 積み木のプレハブ、`Scripts/Outline/PlayerOutlines.cs` |
| オレンジ | 加速 | `GimmickPalette.Accelerate` |
| 青緑 | 減速 | `GimmickPalette.Decelerate` |
| 黄色の点滅 | 予兆（もうすぐ発動する） | `GimmickPalette.Warning` と `GimmickPalette.Blink` |
| 黒に近い暗い色の輪郭 | ギミックが撃った、持ち主のいない攻撃中の積み木 | `PlayerOutlines` の `m_neutralColor` |

- **鮮やかな色は、プレイヤーと積み木のためにとっておく**。画面でいちばん目立つのはプレイヤー、次が積み木、という順番を崩さない。
- 目立つ順は **プレイヤー ＞ 積み木 ＞ 発動中のギミック ＞ 待機中のギミック ＞ 床 ＞ ステージの外の飾り**。
- 色だけで区別しない。危険や種類は、形・動き・点滅でも伝える（赤と緑を見分けにくい人もいる）。

### 1-2. ギミックの色を、その場で新しく決めてしまう
- **NG**: 新しいギミックを作るたびに、ピンク・紫・水色など、その場で選んだ色を付ける。
- **なぜ駄目か**: ギミックの種類の数だけ色が増え、プレイヤーは色から働きを読み取れなくなる。
- **OK**: 色は**働き**で決める。`Assets/Nakagawa/Scripts/Gimmicks/Common/GimmickPalette.cs` の色を既定値にする。
  - 当てはまる意味がないときは、勝手に色を増やさず、人に確認してから `GimmickPalette` に足し、上の表も直す。
  - ギミックの**種類**の違いは、色ではなく形と動き（回る・せり上がる・押し出す）で伝える。
  - 見立ての都合で決まった色がどうしても要るとき（ルーレットの赤と黒など）は、彩度を落とすか、面積を小さくする。

### 1-3. 床・壁・背景を鮮やかにしすぎる
- **NG**: 鮮やかな赤の枠、鮮やかな緑の台、原色のタイルなど、ステージの土台に強い色を使う。
- **なぜ駄目か**: 積み木とプレイヤーの色（赤・青・黄・緑）が床に溶けて、どこにいるか追えなくなる。
- **OK**:
  - 床・壁は**彩度を低く、明るさは中くらい**にする（明るすぎると輪郭やエフェクトが飛び、暗すぎると影や暗い輪郭が見えない）。
  - 1つのステージで強く使う色（アクセント）は **1〜2色まで**。
  - 床の模様は細かくしない。細かい模様の上では、小さい積み木が見えなくなる。

### 1-4. ギミックが、待機中も目立ちすぎる
- **NG**: 広い床のパネルが、発動していない間も鮮やかな色と強い模様で光っている。
- **なぜ駄目か**: 画面の中で広い面積がずっと主張していると、プレイヤーの目がそこに取られる。ギミックを足すほどひどくなる。
- **OK**: **待機中は地味に、発動の直前と発動中だけ目立たせる**。
  - 待機中は、縁取り・薄い模様・低い彩度で「ここにある」ことだけ伝える。
  - 発動の直前は黄色の点滅（予兆）、発動中は働きの色（加速のオレンジなど）をはっきり出す。
  - 常に効いている床（加速の床・氷など）も、塗りつぶさずに模様や縁で見せ、積み木が上に乗っても見分けられる濃さにする。

### 1-5. エフェクトが長く残って画面をおおう
- **NG**: 炎や煙の軌跡が長く濃く残る。当たるたびに大きい火花が出る。
- **なぜ駄目か**: 4人が同時に撃つので、軌跡が画面を何本も横切り、その下のプレイヤーや積み木が隠れる。
- **OK**:
  - 軌跡は短く、薄くする。すぐ消える。
  - 派手さは重要度で分ける。撃墜・必殺技は派手に、ふつうの飛び道具やギミックの動きは控えめに。
  - ギミックのエフェクトに、プレイヤー番号の色（赤・青・黄・緑）を使わない（だれかの攻撃に見える）。

### 1-6. ステージの外の飾りが目立つ
- **NG**: 台の外に、鮮やかで大きい小物（積み木と同じ色の物、積み木と似た形の物）を並べる。
- **なぜ駄目か**: 遊ぶ場所の外なのに目を引き、積み木や脱落したプレイヤーと見間違える。
- **OK**: 外の飾りは彩度を落とす・暗くする・数を減らす。積み木と同じ色と形の組み合わせ（赤い円柱など）は置かない。

### 1-7. HUD の裏に大事な物を置く
- 画面の下には `MatchHud`（`Assets/Nakagawa/Scripts/UI/MatchHud.cs`）の全員分のパネルが並ぶ。カメラの手前側（画面の下の端）に来る床は、パネルの裏に隠れやすい。
- ステージの手前の端に、出現位置・生成エリア・予告の印のように**見えないと困る物**を寄せない。

### 1-8. 見やすさの確かめ方
- スクリーンショットを**白黒**にして、プレイヤー・積み木・ギミック・床が明るさで見分けられるか見る。
- スクリーンショットを **4分の1に縮めて**、4人の位置がすぐ分かるか見る。
- 積み木を床いっぱいに散らし、4人が同時に撃っている状態で確かめる（何もない状態で見やすいのは当たり前）。
- 自分で確かめられないときは、確かめていないと報告に書く。
- キャラの見た目（頭の色など）や名前の表示は他の担当。ステージの作業では変えず、気づいたことは報告にとどめる。

## 2. 表示・UI

### 2-1. ギミックの発動を、発動した座標に文字で出してしまう（特に多い）
- **NG**: 扇風機が動き出したら扇風機の上に「強風！」、ワープしたらゲートの上に「ワープ！」のように、ワールド空間の `TextMesh` や `TextMeshPro` をギミックの位置に出す。
- **なぜ駄目か**: 一画面に4人が映る見下ろしのカメラでは、ワールドの文字は小さく、物や積み木に隠れ、斜めにつぶれて読めない。プレイヤーは自分のキャラを見ているので、離れた場所の文字には気づかない。
- **OK**: 情報を2つに分けて出す。
  - **「何が起きたか」** は **画面の UI**（Screen Space - Overlay のキャンバス）に出す。画面上部など、他の UI と重ならない場所に短く出してすぐ消す。
  - **「どこで起きるか」** は文字を使わず、**床に置く印**（予告の円・矢印・点滅・色）や、ギミック自体の動き、エフェクト、音で伝える。いわだるの必殺技の予告円が、この形の例。
- 画面下は `MatchHud` の全員分のパネルが並ぶので使わない。
- 画面の告知には `StageMessageUI.Show`（`Assets/Nakagawa/Scripts/UI/StageMessageUI.cs`）を使う。画面の上の方に短く出て、自動で消える。新しい告知 UI を別に作らない。
- 床に平らに書いた模様としての文字（ルーレットの数字など）は背景の一部なので、この注意の対象外。ただし、読めないと遊べない情報を床の文字だけで伝えない。

### 2-2. その他の表示の失敗
- **文字に頼りすぎる**: 遊び方は、形・色・動きで伝わるようにする。説明の文字は最後の手段。
- **日本語が表示できない**: `LegacyRuntime.ttf` などの内蔵フォントには日本語がない環境がある。文字を出すなら、プロジェクトの日本語フォント（TextMesh Pro のフォントアセット）を使う。
- **英語の表示**: ゲーム内の文字は日本語にそろえる（「WARNING」ではなく「あぶない！」など、世界観に合う言葉）。
- **画面の UI を増やしすぎる**: 画面の UI も情報のひとつ。常に出しておく表示は増やさず、出したらすぐ消す。

## 3. 遊びの設計

### 3-1. 予告のない即死
- 落下・押し出し・砲撃などで脱落するギミックには、**発動の前に予告**（床の印、ギミックの予備動作、音）を必ず入れる。避けられない死は理不尽に感じる。
- 「ランダムで突然起きる」より、「周期が読める」「動きが見える」ギミックにする。読めれば駆け引きになる。

### 3-2. ゲームの核を消してしまう
- 壁が一つもないと、弾が場外に消えて**跳ね返り・打ち返し・連鎖**が起きにくい。壁が全周にあると、場外への落下がなくなる。どちらにするかは意図して決め、`Flow` に書く。
- 積み木の生成エリアが散らばりすぎると取り合いが起きない。少なすぎると全員が積めない。**取り合いになる場所**を作る。
- ギミックが強すぎて、プレイヤーどうしが戦わずにギミックだけで勝負が決まる構成にしない。主役はプレイヤーの撃ち合い。

### 3-3. 積み木の重さを忘れる
- 積み木を積むほど遅くなり、ジャンプ力が下がる。**10個ではジャンプできない**。
- ジャンプしないと渡れない隙間や段差だけで道をつなぐと、積んだ人が閉じ込められる。必ず歩いて通れる道を残す。
- 首だけ（0個）のスタート直後に、遠くまで行かないと積み木がない配置は避ける。

### 3-4. 不公平な配置
- 出現位置4か所は、生成エリア・ギミック・崖への距離が**ほぼ同じ**になるようにする（対称な配置が基本）。
- 2人対戦でも、出現位置の4か所のうち使われるのは一部。どの組み合わせでも不公平にならないか確認する。
- 出現位置のすぐ近くに危険なギミックを置かない（出現直後の事故）。

### 3-5. 画面に収まらない・見えない
- 一画面で4人全員を映すので、ステージが広すぎるとカメラが引いてキャラが小さくなる。既存の本編ステージの広さ（だいたい 20〜30m 四方）を目安にする。
- 高い壁・大きな小物・背景が、見下ろしのカメラからプレイヤーや積み木を隠さないようにする。
- ギミックを詰め込みすぎない（本編は **1ステージ2種類まで**）。種類が2つでも、置く数と面積が多いと見づらい。ギミックが床に占める広さも抑える（「1. 色と見やすさ」を参照）。

## 4. 世界観

- **スケールの見立てを崩さない**: 本編ステージは「身の回りの物の上に積んだ物の上で戦う、小さな世界」。人間サイズの建物や、見立てのない抽象的な床を出さない。
- **名前を汎用にしない**: 「炎のステージ」「ステージ18」のような名前ではなく、背景にある物の見立て（「お盆の上」「蚊取り線香の渦」）で付ける。
- **設定を勝手に増やさない**: `WorldSetting.md` で【案】の設定を、確定した事実として書かない。キャラの過去や、他校の情報を新しく作らない。
- **黒幕の正体を明かさない**: だるまおとし関連の伏線（片目のだるま人形・小槌など）は、隠しストーリー前のステージでは小物として置く程度にする。
- **特定のキャラを有利・不利にしすぎない**: 例えば赤い積み木しか湧かない、壁だらけ（いわだるが不利）などは、意図がない限り避ける。

## 5. 実装

- **シーンを手で直さない**: ステージは `StageBuilder.cs` の定義からメニューで生成される。シーンだけを直しても、次に作り直したときに消える。直すのは定義の方。
- **既存の定義の途中に追加しない**: ステージの id（`Stage01`…）は `Add` を呼んだ順の通し番号。途中に入れると、後ろのステージの id が全部ずれる。新しいステージは、シリーズの**最後に追加**する。
- **既存のステージを書き換えない**: 頼まれたステージ以外の定義・数値は変えない。
- **検証を通す**: 生成時の `Validate` の結果（出現位置4か所・生成エリア6か所以上・ギミック2種類まで・床からはみ出していないか）が「OK」になるまで直す。警告を無視して完了にしない。
- **回転台の下に床を置く**: 回転台には当たり判定がない。
- **色を直接書かない**: ギミックの色は `GimmickPalette` の色を既定値にする。スクリプトごとに `new Color(...)` で新しい色を決めない。
- **触ってよい場所**: 編集は `Assets/Nakagawa/` の中だけ。セレクト画面の一覧（`Fujihara/ステージ一覧を更新`）やネット対戦用のシーン（`Tools/ネット対戦/NetStages を AllStages から作り直す`）への反映は、担当者に確認してから行う。
- **`.meta` を消さない・作り直さない**: GUID が変わると参照が壊れる。
- **ネット対戦を壊さない**: ギミックの動きを `Random` や各 PC の時間だけで決めると、ネット対戦でホストとクライアントの見た目がずれる。新しい動き方のギミックを作るときは `Docs/NetworkHandoff.md` を読む。
- **重くしない**: 毎フレームの `FindObjectsByType`、大量のライト・パーティクル、動く物理オブジェクトの出しすぎに注意する。

---

## 6. 報告

- **遊んでいないのに「楽しい」と書かない**: `Flow` は狙っている展開。実際に遊んで確かめたことと、狙いを分けて書く。
- **見ていないのに「見やすい」と書かない**: 見やすさを画面で確かめたか、確かめていないかを書く。
- **「完了」の前に**: 生成した結果の `Validate` の結果と、変えたファイルの一覧を報告する。見た目と遊び心地の最終確認は人が `AllStages.unity` で行う、と伝える。
