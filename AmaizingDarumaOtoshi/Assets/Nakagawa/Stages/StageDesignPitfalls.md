# ステージ設計の注意点（モデル向け）

AI がステージを設計・実装するときに起こりがちな失敗と、その避け方。
世界観と仕様は同じフォルダの `WorldSetting.md` を先に読むこと。設計案を出す前と、実装を終えたあとに、このチェックリストを見直す。

---

## 1. 表示・UI

### 1-1. ギミックの発動を、発動した座標に文字で出してしまう（特に多い）
- **NG**: 扇風機が動き出したら扇風機の上に「強風！」、ワープしたらゲートの上に「ワープ！」のように、ワールド空間の `TextMesh` や `TextMeshPro` をギミックの位置に出す。
- **なぜ駄目か**: 一画面に4人が映る見下ろしのカメラでは、ワールドの文字は小さく、物や積み木に隠れ、斜めにつぶれて読めない。プレイヤーは自分のキャラを見ているので、離れた場所の文字には気づかない。
- **OK**: 情報を2つに分けて出す。
  - **「何が起きたか」** は **画面の UI**（Screen Space - Overlay のキャンバス）に出す。画面上部など、他の UI と重ならない場所に短く出してすぐ消す。
  - **「どこで起きるか」** は文字を使わず、**床に置く印**（予告の円・矢印・点滅・色）や、ギミック自体の動き、エフェクト、音で伝える。いわだるの必殺技の予告円が、この形の例。
- 画面下は `MatchHud`（`Assets/Nakagawa/Scripts/UI/MatchHud.cs`）の全員分のパネルが並ぶので使わない。
- いまのプロジェクトには、ギミック用の画面の告知 UI がまだない。必要なら作る前に人に確認し、HUD の担当（Nakagawa）のフォルダに作る。
- 床に平らに書いた模様としての文字（ルーレットの数字など）は背景の一部なので、この注意の対象外。ただし、読めないと遊べない情報を床の文字だけで伝えない。

### 1-2. その他の表示の失敗
- **文字に頼りすぎる**: 遊び方は、形・色・動きで伝わるようにする。説明の文字は最後の手段。
- **日本語が表示できない**: `LegacyRuntime.ttf` などの内蔵フォントには日本語がない環境がある。文字を出すなら、プロジェクトの日本語フォント（TextMesh Pro のフォントアセット）を使う。
- **英語の表示**: ゲーム内の文字は日本語にそろえる（「WARNING」ではなく「あぶない！」など、世界観に合う言葉）。
- **色だけで区別する**: 積み木の色（赤・青・緑・黄）とギミックの警告色がまぎれないようにする。危険は点滅や形でも伝える。

## 2. 遊びの設計

### 2-1. 予告のない即死
- 落下・押し出し・砲撃などで脱落するギミックには、**発動の前に予告**（床の印、ギミックの予備動作、音）を必ず入れる。避けられない死は理不尽に感じる。
- 「ランダムで突然起きる」より、「周期が読める」「動きが見える」ギミックにする。読めれば駆け引きになる。

### 2-2. ゲームの核を消してしまう
- 壁が一つもないと、弾が場外に消えて**跳ね返り・打ち返し・連鎖**が起きにくい。壁が全周にあると、場外への落下がなくなる。どちらにするかは意図して決め、`Flow` に書く。
- 積み木の生成エリアが散らばりすぎると取り合いが起きない。少なすぎると全員が積めない。**取り合いになる場所**を作る。
- ギミックが強すぎて、プレイヤーどうしが戦わずにギミックだけで勝負が決まる構成にしない。主役はプレイヤーの撃ち合い。

### 2-3. 積み木の重さを忘れる
- 積み木を積むほど遅くなり、ジャンプ力が下がる。**10個ではジャンプできない**。
- ジャンプしないと渡れない隙間や段差だけで道をつなぐと、積んだ人が閉じ込められる。必ず歩いて通れる道を残す。
- 首だけ（0個）のスタート直後に、遠くまで行かないと積み木がない配置は避ける。

### 2-4. 不公平な配置
- 出現位置4か所は、生成エリア・ギミック・崖への距離が**ほぼ同じ**になるようにする（対称な配置が基本）。
- 2人対戦でも、出現位置の4か所のうち使われるのは一部。どの組み合わせでも不公平にならないか確認する。
- 出現位置のすぐ近くに危険なギミックを置かない（出現直後の事故）。

### 2-5. 画面に収まらない・見えない
- 一画面で4人全員を映すので、ステージが広すぎるとカメラが引いてキャラが小さくなる。既存の本編ステージの広さ（だいたい 20〜30m 四方）を目安にする。
- 高い壁・大きな小物・背景が、見下ろしのカメラからプレイヤーや積み木を隠さないようにする。
- ギミックを詰め込みすぎない（本編は **1ステージ2種類まで**）。

## 3. 世界観

- **スケールの見立てを崩さない**: 本編ステージは「身の回りの物の上に積んだ物の上で戦う、小さな世界」。人間サイズの建物や、見立てのない抽象的な床を出さない。
- **名前を汎用にしない**: 「炎のステージ」「ステージ18」のような名前ではなく、背景にある物の見立て（「お盆の上」「蚊取り線香の渦」）で付ける。
- **設定を勝手に増やさない**: `WorldSetting.md` で【案】の設定を、確定した事実として書かない。キャラの過去や、他校の情報を新しく作らない。
- **黒幕の正体を明かさない**: だるまおとし関連の伏線（片目のだるま人形・小槌など）は、隠しストーリー前のステージでは小物として置く程度にする。
- **特定のキャラを有利・不利にしすぎない**: 例えば赤い積み木しか湧かない、壁だらけ（いわだるが不利）などは、意図がない限り避ける。

## 4. 実装

- **シーンを手で直さない**: ステージは `StageBuilder.cs` の定義からメニューで生成される。シーンだけを直しても、次に作り直したときに消える。直すのは定義の方。
- **既存の定義の途中に追加しない**: ステージの id（`Stage01`…）は `Add` を呼んだ順の通し番号。途中に入れると、後ろのステージの id が全部ずれる。新しいステージは、シリーズの**最後に追加**する。
- **既存のステージを書き換えない**: 頼まれたステージ以外の定義・数値は変えない。
- **検証を通す**: 生成時の `Validate` の結果（出現位置4か所・生成エリア6か所以上・ギミック2種類まで・床からはみ出していないか）が「OK」になるまで直す。警告を無視して完了にしない。
- **回転台の下に床を置く**: 回転台には当たり判定がない。
- **触ってよい場所**: 編集は `Assets/Nakagawa/` の中だけ。セレクト画面の一覧（`Fujihara/ステージ一覧を更新`）やネット対戦用のシーン（`Tools/ネット対戦/NetStages を AllStages から作り直す`）への反映は、担当者に確認してから行う。
- **`.meta` を消さない・作り直さない**: GUID が変わると参照が壊れる。
- **ネット対戦を壊さない**: ギミックの動きを `Random` や各 PC の時間だけで決めると、ネット対戦でホストとクライアントの見た目がずれる。新しい動き方のギミックを作るときは `Docs/NetworkHandoff.md` を読む。
- **重くしない**: 毎フレームの `FindObjectsByType`、大量のライト・パーティクル、動く物理オブジェクトの出しすぎに注意する。

---

## 5. 報告

- **遊んでいないのに「楽しい」と書かない**: `Flow` は狙っている展開。実際に遊んで確かめたことと、狙いを分けて書く。
- **「完了」の前に**: 生成した結果の `Validate` の結果と、変えたファイルの一覧を報告する。見た目と遊び心地の最終確認は人が `AllStages.unity` で行う、と伝える。
